# 17.1: A countdown that runs out while you are on another page

**Parent:** 17 (Countdown completion sound)

17 closed with this in its **Out of scope**: "playing the sound when the
countdown expires while the user is on a page other than /timer — the
auto-stop itself only fires from the timer page today". That is the bug,
reported from the live app.

The auto-stop lived in `RunningTimer`, inside `TimerControls`, which mounts
only while `/timer` is open. A countdown that ran out anywhere else was
watched by nothing, which produced all three symptoms at once:

- **No alarm.** Nothing was listening for the expiry.
- **The nav readout never cleared.** The session was never stopped, so
  `TimerBar` kept rendering, pinned at `00:00` by its own `Math.max(0, …)`.
- **The alarm fired on arrival, and wrote duplicate entries.** Returning to
  `/timer` mounted `RunningTimer` fresh, so `autoStopFired` — a `useRef`, one
  per mount — was a clean guard over an already-expired countdown. It sounded
  and stopped. Bounce between pages before the server row clears and each
  visit writes another entry with the same title and times.

**Blocked by:** 17 — done

**Status:** done (2026-09-20)

- [x] The expiry watch moves to `useCountdownExpiry`, mounted once in
      `AppLayout` beside `useTimerSync`, so it runs on every page (R2b)
- [x] The guard is module-level and keyed by `id:created_at`, so it survives
      navigation and cannot be reset by a remount
- [x] One `setTimeout` for the remaining time rather than a half-second tick,
      so watching app-wide does not re-render every page every 500ms
- [x] The entry records the countdown's own length, not the overrun: a tab
      that was closed, asleep, or elsewhere notices late, and the session
      should be the one that was asked for
- [x] `RunningTimer` keeps the readout and loses the auto-stop
- [x] Tests: the alarm, the entry and the nav readout clearing with the page
      on /settings; one entry however many times /timer is revisited

**Not a new requirement:** R2b already says "when a countdown timer reaches
zero", with no mention of which page is open. The behaviour was out of step
with it, not ahead of it.

**Known limit:** a tab that is fully closed still notices nothing — the
expiry fires on the next load, and the entry is dated from the real expiry
instant. Push notification of an expiry is R33c/R33d territory (iOS), not
this ticket.
