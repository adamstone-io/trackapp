# 17.2: Stopping a session is one atomic step

**Parent:** 17 (Countdown completion sound)

17.1 moved the countdown watch to the app layout and guarded it with a
module-level flag. The duplicate entries came back anyway, which is the
guard's own limit: **module-level means per JavaScript context, which means
per browser tab.** Two tabs open is two independent guards, each finding the
same expired session and each recording it. No guard living in one browser's
memory can fix that — the tabs share nothing except the server row.

The stop was also two requests: `POST /time-entries/`, then
`DELETE /active-timer/`. Between them the session was still live to everybody
else, and that window is *seconds* wide, because `persistEntry` first calls
`ensureTaskId`, which walks every page of `/tasks/` (see ticket 21).

**Blocked by:** 17.1 — done

**Status:** done (2026-09-20)

- [x] `POST /api/active-timer/stop/` records the entry and releases the
      session inside one transaction, holding the row with `select_for_update`
- [x] The row is the lock: whoever takes it writes the entry, everyone
      arriving afterwards gets 404 and writes nothing — across tabs, devices
      and reloads alike
- [x] The server computes the duration from its own row and clamps a
      countdown to the length it was set for, so noticing late cannot stretch
      the entry. That now holds for every client, not just the web app
- [x] The server resolves the task by normalised title in one query, so the
      stop path no longer walks `/tasks/` at all (part of ticket 21, for this
      path only)
- [x] A 404 makes the tab take back the row it drew optimistically and refetch
      the day's log, so what shows is what the tab that won recorded
- [x] The expiry check also runs on `visibilitychange`: a hidden tab's timers
      are throttled to a minute or worse and a sleeping machine runs none, so
      being looked at again is its own reason to check
- [x] The empty-session 404 names itself `code: "no_active_timer"`, and the
      client matches the code rather than the status. An API without this
      endpoint answers 404 too, and a client reading that as "already
      recorded" would bin the session without a word — which is exactly what
      happens for as long as the static site is deployed ahead of the API
- [x] `ApiError` carries the body's `code`, the way the trial-expired path
      already relied on one
- [x] Django tests for the second stop, the countdown clamp, pauses, task
      reuse, and one person's stop not touching another's session

**Deploy order:** API first is safe — the endpoint sits unused and the old
bundle's two-request stop still works, since neither `POST /time-entries/` nor
`DELETE /active-timer/` was removed. Frontend first is the risky direction,
and the `code` check is what makes it fail loudly instead of silently.

**Still true:** a tab that is fully closed notices nothing until something
opens. The entry is dated from the real expiry instant, so the data is right
and only the alarm is late.

**Not done here:** `ensureTaskId` still walks every task for manual entries
and title edits — ticket 21 stands for those paths.
