# 06.9: The study list pages as you scroll

**Parent:** 06 (Study page core)

**What to build:** the page fetched the whole collection before drawing a
single row — `fetchAllPages` walked every page of a paginated endpoint, twenty
at a time, one request waiting on the last. At ~2,300 items that is ~118
sequential round trips, and the page sat blank for minutes (R57 says 500ms).
It should load twenty, then twenty more as the list is scrolled.

The ordering and the filtering had to move to the server with it: you cannot
sort or narrow a collection you have only seen the first twenty rows of.

**Blocked by:** 06 — done

**Status:** done (2026-09-20)

- [x] `GET /study-items/` orders least-recently-touched first, never-touched
      ahead of those, with a total order so no row lands on two pages (R31w)
- [x] `archived=true|false` splits the two lists the page shows; absent, both
      come back as before
- [x] `category` prefix-matches instead of requiring equality, matching the
      filter box (R31y)
- [x] The list serializer drops `today_count`/`week_count`/`month_count` —
      each walked a row's whole timestamp array in Python and no client read them
- [x] The page uses `useInfiniteQuery` with a scroll sentinel at the foot of
      each list (R31x)
- [x] The filter box is debounced and holds its rows while the new page loads
- [x] Optimistic updates rewritten against the paged cache; archive/restore
      moves a row between the two lists
- [x] The chrome renders while the first page is in flight — no blank screen

**Not done here:** `fetchAllPages` still backs projects, habits and tasks.
Habits and projects are small, but the task list will need the same treatment
before it grows.
